Technical reference

How LinkedIn Content Studio is built

A modular-monolith Turborepo that turns a professional's real background into grounded LinkedIn posts — three ways to reach a topic, a swappable AI/news/storage provider layer, and a deterministic-first pipeline that only spends model calls where judgment actually adds value.

apps/web React 19 + Vite apps/api Fastify 5 + Drizzle + Postgres packages/shared Zod contracts

01System overview

03Provider isolation

Every volatile capability is an interface

ADR-002 set this rule before any vendor was chosen: domain code depends on an interface, never an SDK. It paid off twice this session — once when the OpenAI account ran dry (ADR-007), once when the same thing blocked images (ADR-008). Neither fix touched a prompt, a schema, or a route.

No OpenAIService god object — text and image generation are separate capabilities even when both happen to use OpenAI.
Why this mattered in practice: switching text providers was a one-line env change plus one new adapter file. The real cost showed up one layer up — Claude's models reject the temperature param on current versions, and are more verbose than GPT-4.1, which broke schema max-lengths in two prompts until they got explicit character-count hints. The interface boundary held; the prompt layer absorbed the vendor difference, exactly where ADR-002 intended it to.

04Three topic paths

One pipeline, three ways in

Discover News is the only path where the model evaluates and scores candidates. Content Plan and Custom Topics are pre-vetted input — the user already did the vetting, so both build the opportunity deterministically and skip the AI evaluation step entirely.

  Persona --> Plan["Content Plan
(deterministic) 24 pre-approved topics"]
  Persona --> Custom["Custom Topics
(deterministic) user-authored idea"]
  Discover -->|"source: discover"| Select[OpportunityService.select]

Discover NewsLive NewsAPI results, filtered + rankedYes — model scores & writes why-this-fitsModel-suggested

Custom TopicsTitle, hook, key points typed by the userNo — user already vetted their own ideaPicked directly by the user
The bug this design exposed: until ADR-009, "Write post" resolved the selected opportunity via a lookup hardcoded to source: "discover". Selecting a Content Plan or Custom topic updated its own row correctly — but generation silently used whichever opportunity Discover had last selected instead. It shipped a plausible, wrong post rather than an error, which is why it survived until live testing caught it.

07Data model

Insert-only history where regeneration matters

generated_posts and generated_images never update in place — every generate/edit/retry is a new row, so regeneration can never silently erase a publishable result. Status rows (content_plan_topics, custom_topics) are the opposite: mutable, because "Planned → Selected → Published" is one topic's lifecycle, not a history to preserve.

08Frontend architecture

One page, a step machine, no router

App.tsx holds a single StepId union and renders one view component per step. There is no client-side router — the whole product is one URL, and navigation is a state transition, not a route change. This matches the single-workspace, no-auth model (ADR-003).

Each box is a React component in apps/web/src/ (ContentPlanView, CustomTopicsView, DiscoverView, PostView, PostHistoryView…). All of them call the API through one shared boundary, api.ts — no component calls fetch() directly.

ADR-001

Modular monolith in Turborepo with Docker Compose

Accepted

Context

The MVP needs a React frontend, a Fastify API, PostgreSQL, and a reproducible local environment. The prompt suggested several packages. Microservices, Kubernetes, and extra infrastructure would make the demo look sophisticated and finish late.

Options considered

  1. Separate repositories for web and API
  2. Microservices per domain module
  3. Modular monolith in one Turborepo, Compose for local runtime
  4. Frontend-only app calling OpenAI directly

Decision

Use a Turborepo modular monolith: apps/web, apps/api, packages/shared, packages/config. Run web, api, and postgres with Docker Compose. Do not extract ai or database packages until a second consumer exists. Do not put OpenAI keys in the frontend.

Consequences

  • One deployable API, clear module folders
  • Shared types without sharing implementations
  • Compose is the documented developer path
  • Future extraction of a provider package is possible but not prepaid

Tradeoffs

Turborepo adds some workspace ceremony. That cost is lower than splitting services or duplicating types.

ADR-002

Provider isolation for OpenAI, news, and storage

Accepted

Context

The MVP uses OpenAI for text and images, a third-party news API, and local disk for media. These vendors will appear in tests, failures, and possibly replacements. Coupling use cases to SDKs would make domain tests require live APIs.

Options considered

  1. Direct SDK calls from routes and use cases
  2. One OpenAIService for all AI plus ad-hoc fetch for news
  3. Narrow interfaces: TextGenerationProvider, ImageGenerationProvider, NewsProvider, StorageProvider

Decision

Isolate volatile boundaries only. Text and image generation are separate interfaces even though both are OpenAI in the MVP. Storage is an interface with LocalStorageProvider. News is an interface with a NewsAPI.org adapter. Application models never accept OpenAI, NewsAPI, or filesystem types. Automated tests use deterministic fakes.

Consequences

  • Use cases can be tested without network
  • Replacing NewsAPI or moving storage to object storage does not rewrite domain rules
  • Slightly more types at the start

Update — second TextGenerationProvider adapter

AnthropicTextGenerationProvider (Claude) was added alongside OpenAITextGenerationProvider, selected at startup via TEXT_PROVIDER=openai|anthropic in apps/api/src/app.ts. This is the payoff of isolating TextGenerationProvider: persona, opportunity, and post generation code did not change — only app.ts's provider construction and env.ts's schema did. Anthropic's Messages API has no strict JSON response mode equivalent to OpenAI's response_format: json_object, so the adapter appends a short "respond with JSON only" instruction to the system prompt; parseJsonObject() (already used for both providers) still strips any stray markdown fences.

Tradeoffs

Four interfaces is enough. Generating interfaces for Postgres or Fastify would be theater.

ADR-003

Unauthenticated single-workspace MVP

Accepted

Context

The product journey starts at a professional profile. The prompt never required login, teams, or multi-tenant isolation. Auth would consume a slice that does not demonstrate personalized authority.

Options considered

  1. Full signup/login before profile
  2. Magic-link or OAuth with a User table
  3. Profile is the aggregate root in a local workspace, no auth

Decision

Ship without user accounts. The local deployment holds one working profile/workspace. Security still applies to uploads, prompts, keys, and validation. Missing auth is not missing input validation.

Consequences

  • Slice 1 can show product value immediately
  • A later User/Auth ADR will be required before any shared or hosted multi-user deployment
  • No personal data access-control model exists yet; the demo is trusted-local

Tradeoffs

This is unacceptable for a public multi-user service. It is acceptable for the Compound Engineering MVP demo.

ADR-004

NewsAPI.org as the concrete NewsProvider

Accepted

Context

The product must discover recent technology events without fabricating them and without coupling domain logic to a vendor. Official blogs are higher quality than aggregators, but a persona-specific search needs a query API.

Options considered

  1. Curated RSS only from official engineering blogs
  2. LLM-invented "news" (rejected: factual integrity)
  3. Tavily/Exa/Firecrawl semantic web search
  4. NewsAPI.org search with recency and preferred domains
  5. Scrape Google News (rejected: brittle, legally noisy)

Decision

Use NewsProvider.searchNews(topics, dateRange) and implement NewsApiNewsProvider for the MVP. Prefer high-quality domains when the adapter can constrain sources. Persist normalized NewsArticle records. Rank and reject in the relevance module, not in the adapter. Full article bodies are not required for MVP discovery — title, description, source, URL, and published date are enough for traceability.

Consequences

  • Local demo needs NEWS_API_KEY
  • Free NewsAPI terms are development-oriented; production use would need a license change or a new adapter
  • Quality still depends on relevance rejection, because aggregators are noisy

Tradeoffs

RSS would be cleaner and poorer at matching arbitrary personas. Semantic search tools may return better pages later; the interface allows replacement without domain rewrite.

ADR-005

User-paced generation instead of a background pipeline

Accepted

Context

Persona, research, opportunities, post reviews, and image generation can exceed a comfortable single HTTP timeout. The user also must choose a topic and an angle. A hidden 90-second job would remove the product's trust surfaces.

Options considered

  1. One API call that runs the full pipeline
  2. Redis/queue/worker with job polling
  3. User-paced HTTP use cases; frontend walks the journey; durable state in Postgres

Decision

Each stage is an explicit use case. The UI shows intermediate results. Postgres holds the ContentRun. Image generation retries against an existing post. No job platform in the MVP.

Consequences

  • Latency is visible and recoverable per stage
  • Why This Post? and angle selection stay first-class
  • The client is an orchestrator of user decisions, not of domain rules

Tradeoffs

More round trips. That is desirable here. A worker can be introduced later if a stage must run unattended.

ADR-006

Content Plan topics as deterministic synthetic opportunities

Accepted

Context

The user supplied linkedin-technical-publishing-plan.pdf: a fixed 12-week, 24-post editorial calendar with pre-approved briefs. This is a different shape of input than the existing pipeline, which discovers current events via NewsProvider and lets the model evaluate relevance. The plan's topics are already vetted by the user outside the app — running them back through AI opportunity evaluation would add variance and cost without adding value.

Options considered

  1. Extend the schema with a nullable articleId and a new topicId reference, adding a second code path through OpportunityService
  2. Build a fully separate post-generation pipeline for plan topics
  3. Represent each selected plan topic as a synthetic news_articles row plus a deterministically-built OpportunityPayload, created via the existing repositories, with no AI call

Decision

Option 3. ContentPlanService.selectTopic() inserts one synthetic article, builds an OpportunityPayload directly from the brief fields, persists it and marks it selected via the existing OpportunityService.select(), and records topic status in a new table, content_plan_topics. PostService.generate() needs no changes.

Consequences

  • No schema change to news_articles, research_runs, opportunity_sets, or content_opportunities
  • Selecting a plan topic creates its own research run and opportunity set, tagged source: "content_plan" — it does not replace Discover News' own "latest" state (see ADR-009; this was a real bug for a while)
  • Only the 24 approved topics (T01-T24) are imported
  • Only editorial status is tracked (Planned/Selected/Drafted/Published/Skipped) — no LinkedIn analytics API is available

Tradeoffs

A schema extension (option 1) would be more explicit but duplicates code paths for no behavioral gain. Reusing the existing tables through a synthetic article keeps one code path at the cost of a slightly unusual provider value on the article record.

Related

Custom Topics reuses this exact synthetic-opportunity pattern verbatim, source: "custom" instead of "content_plan" — no new ADR needed for it. See ADR-009 for the source-scoping fix this pattern's second and third users made necessary.

ADR-007

Anthropic as a second TextGenerationProvider

Accepted

Context

The OpenAI account used for local development ran out of credits, blocking every AI-dependent step. Anthropic's API was cheaper to fund and the provider interface already existed specifically so a vendor could be swapped without touching domain code.

Options considered

  1. Wait on OpenAI credits / fund the same account
  2. Add AnthropicTextGenerationProvider behind the existing interface, selectable via env var
  3. Replace OpenAI outright

Decision

Add AnthropicTextGenerationProvider implementing the same TextGenerationProvider interface. Select via TEXT_PROVIDER=openai|anthropic, defaulting to openai. Model name is a separate env var per vendor. No prompt, schema, or use case changed.

Consequences

  • Local .env needs either OPENAI_API_KEY or ANTHROPIC_API_KEY depending on TEXT_PROVIDER
  • Current Claude models reject the temperature parameter — the adapter omits it entirely
  • Claude's structured JSON responses were being truncated at 8,000 tokens non-streaming — the adapter streams with max_tokens: 16000 instead, purely for size/timeout headroom, not UX
  • Claude is more verbose than GPT-4.1 for the same instructions, which broke schema max-lengths in two prompts until explicit character-count hints were added — absorbed in the prompt layer, exactly where ADR-002 intended
  • No cost/quality A/B was run; the switch was availability-driven, not benchmarked

Tradeoffs

Keeping both providers alive means two vendor SDKs and two sets of quirks to remember, versus the single-point-of-failure ADR-002 was written to avoid.

ADR-008

Pollinations.ai as a free ImageGenerationProvider

Accepted

Context

The same unfunded OpenAI account also blocked image generation. Anthropic has no image API at all. The question was whether a genuinely free, no-key image API existed that was good enough for demo purposes.

Options considered

  1. Fund the OpenAI account and stay single-provider
  2. Google AI Studio (Imagen) — free tier, still needs an API key
  3. Hugging Face Inference API — free tier, unpredictable rate limits/latency
  4. Pollinations.ai — fully free, no API key, direct HTTP GET

Decision

Add PollinationsImageGenerationProvider. Select via IMAGE_PROVIDER=openai|pollinations, defaulting to openai. The adapter calls a plain GET against image.pollinations.ai and reads raw JPEG bytes — no auth, no client library, no job polling.

Consequences

  • IMAGE_PROVIDER=pollinations needs no API key at all
  • No reference-photo / image-to-image support — OpenAI's images.edit() can use uploaded reference photos, Pollinations ignores that input entirely and generates from the text prompt alone
  • No SLA, no documented rate limits, no uptime guarantee — acceptable for a demo, not for production without revisiting
  • No metadata in the response (no revised prompt, no safety classification) — the adapter normalizes both providers into the same internal model

Tradeoffs

A paid, authenticated provider would offer more predictability at the cost of needing another API key the demo environment didn't reliably have. Pollinations trades predictability for zero setup friction.

ADR-009

Source-scoped "latest selection" instead of one global pointer

Accepted

Context

The MVP had exactly one way to reach a content opportunity: Discover News. Content Plan then added a second way, reusing the same table — this exposed missing scoping, fixed with a first source column. Custom Topics then added a third source value. This is when the remaining bug surfaced during manual testing: OpportunityService.getSelected() — what PostService actually calls when writing a post with no explicit opportunityId — still called getLatest() with no argument, which defaulted to "discover". Selecting a Content Plan or Custom topic updated that source's own selection, but "Write post" kept resolving Discover's selection instead — silently writing about the wrong topic.

Options considered

  1. Have the frontend pass an explicit opportunityId through every "select a topic" → "write post" hand-off
  2. Track "the one true current selection" as its own concept, independent of source
  3. Keep getSelected() hardcoded to "discover" and special-case the other call sites

Decision

Add opportunity_sets.selected_at, stamped every time a set is selected. Add getMostRecentlySelected(): the set with a non-null selection, ordered by selected_at DESC NULLS LAST, across all sources. getSelected() now calls this instead of the source-hardcoded getLatest(). A new GET /api/opportunities/selected route exposes the same resolution to the frontend's staleness check. getLatest() itself stays hardcoded to "discover" on purpose — it answers "what did Discover find," a different question from "what's currently selected."

Postgres orders NULL first in a plain ORDER BY x DESC, not last — the first version of this fix used a plain desc() and still returned a stale, pre-migration row ahead of a genuinely recent selection. The working query uses a raw SQL fragment with an explicit DESC NULLS LAST, since drizzle-orm 0.44 has no nullsLast() chain on desc().

Consequences

  • Every "select a topic" action across all three paths now converges on one correct, source-agnostic notion of "what should Write Post use"
  • Rows created before this migration have selected_at IS NULL and sort behind any real selection — correct for a single-workspace MVP, would need a backfill for multi-tenant
  • Explicit ID-threading (option 1) was rejected because it would have multiplied a UI-state concern to solve what was fundamentally a backend query bug

Tradeoffs

Explicit ID-threading is more predictable — no query ordering to get right — at the cost of every frontend "select" flow needing to carry and hand off an ID. The chosen approach keeps the frontend simple by making the backend's notion of "current selection" actually correct, which is where the bug lived.
